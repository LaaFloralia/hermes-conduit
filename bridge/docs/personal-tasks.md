# Personal Linear tasks

The owner-facing task source uses its own Linear personal API key. It never falls back to the existing agent credential. A Mac-side operator must configure both `LAA_LINEAR_PERSONAL_TOKEN_HELPER` (an absolute path to an executable that prints only the key to standard output) and `LAA_LINEAR_PERSONAL_VIEWER_ID` (the expected Linear user ID) in the Bridge's runtime environment. The helper and credential are provisioned by the owner/operator, not by the iPhone. Neither the key nor helper output belongs in the repository, command arguments, logs, or an iPhone response. When either setting is missing, the key is malformed, or the `viewer` is different, the personal source refuses access. Each operation checks the viewer using the same credential used for its subsequent request.

These authenticated `tasks:read` endpoints are separate from the existing `/v1/tasks` agent view:

- `GET /v1/personal-tasks`: `view=all|mine|active|backlog`, optional `search`, `project`, `cycle`, `customView`, `limit`, and `cursor`. A saved view cannot be combined with other filters. Search and saved view evaluation are performed by Linear.
- `GET /v1/personal-tasks/{id}`: an issue by Linear identifier or `linear:`-prefixed identifier, including its full description.
- `GET /v1/personal-tasks/{id}/{section}`: independently paginated `comments`, `children`, `history`, `relations`, `inverse-relations`, and `attachments`. `GET /v1/personal-tasks/{id}/comments/{commentId}/replies` pages a comment's replies after checking that the parent belongs to the issue. History includes common property, label, relationship and archive changes; unknown activity is identified as such rather than treated as complete.
- `GET /v1/personal-tasks/{id}/files` lists recognized private Linear file links in the description, or in an issue comment selected by `comment`. `/files/{fileId}/content` rechecks that association and `/attachments/{attachmentId}/content` rechecks the attachment's issue before fetching. The response contains base64 bytes and a sanitized name; it is bounded to 20 MiB before and during the download. Markdown URLs that cannot be parsed by the supported link pattern are not listed.
- `GET /v1/task-projects`, `/v1/task-cycles`, `/v1/task-views`, `/v1/task-inbox`: paginated personal collections. Inbox accepts `includeArchived=true|false`; the cursor is bound to that choice. `GET /v1/task-inbox/{id}` reads one notification, including archived ones, after checking its recipient. Reading never marks it read.
- `GET /v1/task-metadata`: first page of choices with a `complete` flag per collection. If a flag is false, the client must not present that subset as complete.
- `GET /v1/task-options?kind=teams|users|states|labels|milestones`: paginated choices. Projects and cycles use the separate collection endpoints above.

Pages contain `items`, `nextCursor`, `observedAt`, and `paginationConsistency: "live"`. Cursors are tied to the filter and viewer. Linear can change between pages, so this is not a snapshot; clients should deduplicate by ID and refresh when needed. Individual issue label sets explicitly include `labelsComplete`.

The source uses fixed GraphQL documents and rejects partial/error responses instead of interpreting them as empty results. No live credential or task data was used for the fixture tests. The current notification relay does not accept Linear events; inbox data does not imply APNs delivery. The phone refreshes Inbox while the screen is in use; there is no background poll or push. An unread indicator describes fetched items, not a complete live count.

## Writes and reconciliation

`POST /v1/personal-tasks` creates an issue; `PATCH /v1/personal-tasks/{id}` updates allowed attributes. Both require `tasks:write`, an `Idempotency-Key`, and the `expectedViewerId` obtained when the draft was prepared. The Bridge refuses a different current viewer before reserving or writing, including on the first attempt. Create requires `teamId` and `title`; create/update accept `description`, `stateId`, `assigneeId`, `priority`, `estimate`, `dueDate`, `projectId`, `projectMilestoneId`, `cycleId`, `parentId`, `teamId`, and `labelIds`. Assignment does not start a worker. Unsupported fields are refused. Responses contain a minimal operation record; the client reads the issue for its current content.

`POST /v1/personal-tasks/{id}/comments` accepts `body` and optional `parentId`; the parent must belong to the same issue. `/relations` accepts `relatedIssueId` and `type` (`blocks`, `duplicate`, `related`, or `similar`), directed from the current issue to the related issue. `/attachments` accepts an HTTPS external `url`, `title`, and optional `subtitle`. Each requires the same viewer and idempotency fields as issue writes. Linear may upsert an attachment by URL: its confirmed `resultId` can differ from the reserved target; for an unknown result inspect the task's links.

`PATCH /v1/task-inbox/{id}` accepts only `expectedViewerId` and `action` (`read`, `unread`, `archive`, `unarchive`) with `tasks:write` and an `Idempotency-Key`. The Bridge rereads the notification and checks its recipient before writing, and confirms the returned ID, viewer and requested state. These are explicit user actions; opening an issue does not change its notification. The phone saves the key and action before the request, and its task queue never automatically sends them. An uncertain result remains in Pending: the single-notification screen also reads archived items to help the owner investigate before confirming a resolution. A current state alone cannot prove what happened if another writer changed it. Linear's actual null-to-unread behavior and authorization must still be checked by the operator using the owner's account.

`POST /v1/personal-tasks/{id}/files` accepts a 1-byte–20-MiB body with a required length, SHA-256 digest, base64 UTF-8 filename, MIME type and original viewer headers. At most two uploads are buffered at a time. The Bridge checks the viewer and device scope, obtains a private Linear upload target, uploads without forwarding the Linear credential, then associates the asset with the task. Linear download credentials are sent only to `uploads.linear.app`; neither download nor upload follows redirects. The upload destination is restricted to Google Cloud Storage hosts. This conservative host assumption and real file compatibility need live verification by the operator. After a definite refusal of the attachment association, the Bridge records the SHA-256 of the newly uploaded asset URL and attempts to delete that asset once through Linear; failure of that cleanup does not change the refusal, and may leave an unattached private asset. If the PUT may have completed but its response was lost before association, an unattached asset may also remain. If association may have happened, the Bridge never deletes the asset: the result remains unknown until reconciled. At most four rejected uploads are drained simultaneously, for at most 32 MiB and five minutes each; when a limit is exceeded, the Bridge sends the original refusal with `Connection: close` and then closes that connection. Actual iOS network behavior still needs verification.

Attribute updates follow Linear's last-write-wins behavior. The Bridge resolves the issue to its immutable ID before writing, so a team move may change its human-readable identifier. An update containing `description` also requires the previously read `updatedAt` as `If-Match`, either raw or in strong quotes. Immediately before the mutation, the Bridge reads the issue again. A mismatch returns 412 with the current issue so the client can compare it with its retained draft and obtain an explicit choice. This check is not an atomic Linear conditional update: a short race remains between the read and the write.

`GET /v1/task-operations/by-key` takes the original `Idempotency-Key` header; `/v1/task-operations/{operationId}` fetches a known operation, and `/v1/task-operations` lists unresolved operations for the same device and viewer. They require `tasks:read` and the expected personal viewer; confirmation requires `tasks:write`. A definite Linear input refusal is recorded as `rejected` without the submitted contents. A retryable failure before any mutation is `preflight_retryable`: the same key and request can retry, while conflicting requests remain blocked. After seven days the Bridge atomically closes such a preflight as rejected so the client can restore its draft. If a Linear request may have arrived but no confirmed response was recorded, the operation stays `outcome_unknown` and is never sent again automatically. Create reserves a UUID before sending; the owner can use that target ID to investigate whether the issue exists. For an update, inspect the target and its activity before deciding.

`POST /v1/task-operations/abandon-unsent` uses the original key and `{ "expectedViewerId": "…" }`. It requires `tasks:read` because it only closes this device's definitely unsent local key and never writes to Linear. It atomically closes an unreserved key or retryable preflight, preventing a delayed original request from writing after the draft is restored. If a write may already have started, it returns the existing state without closing it. This also lets a read-only device recover a request that was refused for lack of write scope.

After that investigation, `POST /v1/task-operations/{operationId}/resolve` with a new `Idempotency-Key` and `{ "confirmed": true, "resolution": "applied" | "not_applied" }` records the owner's conclusion. It does not make a Linear change. A live writer cannot be resolved as a crashed writer just because time elapsed. If the old process has stopped, an unfinished operation becomes unknown after the grace period; PID reuse may delay recovery. The original key returns `operation_resolved` and remains unusable for another write after resolution.

The 0600 task ledger retains hashes, device/viewer/operation identifiers, target/result identifiers, times and states, never titles, descriptions, credentials or full responses. Before reserving or abandoning a key, succeeded and rejected records last updated at least seven days earlier are compacted to tombstones containing the key hash, compaction time, terminal status, and a hash binding the result to the original device and viewer. Tombstones are retained indefinitely: without them, a very old successful request could be mistaken for an unreserved key and a restored draft could create a duplicate. Status and abandon return `410 task_operation_compacted` with the terminal result for the matching viewer; replay remains blocked. In Pending, a confirmed rejection can be explicitly restored as a draft; a success can only be discarded locally after checking Linear. Tombstones from older array or timestamp-only formats retain an unknown result and cannot be treated as rejected. Keys already deleted by a previous retention policy cannot be reconstructed from the ledger; do not regard an absent historical key as proof of non-delivery if that previous policy ran on live data. A tombstone is about 200 bytes in the JSON file: 20,000 records are about 4 MB for this single-user service, with indefinite growth. Resolved and unresolved records are retained; the 20,000 limit applies to full records and still stops new writes if those fill it. The JSON ledger is still read and rewritten for reservation and completion; compaction only reduces full-record size. Loss or corruption of the ledger after initialization refuses new writes pending operator recovery. The local files are not tamper-proof against the same macOS user.

The iPhone stores pending task requests and attachments in its protected Work draft store. Pending remains accessible when Keychain, pairing, the Mac or the viewer is unavailable: before viewer verification, entries are anonymous and may only be explicitly discarded locally, not read, moved or sent. On a successful task-list refresh or Pending refresh while the app is open, it checks each original key before sending only a request that has no Bridge record or is marked `preflight_retryable`; ambiguous or rejected results stay pending. A create's queued comment, child, relation or link waits until the same viewer's create is confirmed and the exact issue is read back. Retries keep the original key and description version. After six days, the phone stops automatic repeats but still permits status checks and reconciliation. This is foreground processing, not background delivery; opening the task screen after reconnection is required. Unsent drafts need a previously loaded viewer and task/team choices, and rejected follow-ups must be copied into a new request after checking their state.

Re-pairing creates a different device ID, and changing the configured Linear viewer also changes the local scope. The phone's Pending screen counts such former submissions under “別の端末・別の本人” without showing their contents. The owner must explicitly choose “破棄” or “この端末の下書きへ移す”; moving preserves the protected original request, its idempotency key and original device/viewer binding. It does not send it. A moved request stays quarantined, including an unknown result, and the editor cannot retry it against the new device's ledger. To recover it, reconnect the original viewer; if it appears under “別の端末・別の本人” again, explicitly move it into that viewer's current scope before choosing its status action in Pending. The Bridge's `original-status`, `original-abandon`, and `original-resolve` actions require an authenticated new device, the registered original device ID, the original viewer and the original key. Status returns the original reserved target UUID while its full record remains; abandon atomically closes only a definitely unsent key; resolve records the owner's explicit determination without sending to Linear. The registered old device entry and ledger must still exist. If the original viewer is unavailable, the request remains quarantined. After a confirmed rejection or not-applied result, restore the draft and deliberately create a new request only after inspection; an applied full record clears the local submission; a compacted success requires explicit local discard. A moved follow-up returns to its normal editor only after the original parent operation and the same Linear issue are verified. If the parent cannot be verified (including after its record has been compacted), the content remains in Pending for manual inspection rather than being sent or silently discarded; the owner may copy the content and explicitly discard it. Discarding the local copy does not erase or resolve a Mac ledger entry, and does not prove that Linear did not apply it. For create and update records, Pending offers “Open Task” only after a matching issue has been read back and its Linear identifier confirmed.

No canonical Linear issue-to-Paseo-session mapping was found in the inspected Bridge/session and personal-agent contracts. The Inbox and task views therefore do not infer execution status from an assignee or launch a worker; task-specific delegation remains unavailable until that mapping and its confirmation flow are established.
