# Personal Linear tasks

The owner-facing task source uses its own Linear personal API key. It never falls back to the existing agent credential. A Mac-side operator must configure both `LAA_LINEAR_PERSONAL_TOKEN_HELPER` (an absolute path to an executable that prints only the key to standard output) and `LAA_LINEAR_PERSONAL_VIEWER_ID` (the expected Linear user ID) in the Bridge's runtime environment. The helper and credential are provisioned by the owner/operator, not by the iPhone. Neither the key nor helper output belongs in the repository, command arguments, logs, or an iPhone response. When either setting is missing, the key is malformed, or the `viewer` is different, the personal source refuses access. Each operation checks the viewer using the same credential used for its subsequent request.

These authenticated `tasks:read` endpoints are separate from the existing `/v1/tasks` agent view:

- `GET /v1/personal-tasks`: `view=all|mine|active|backlog`, optional `search`, `project`, `cycle`, `customView`, `limit`, and `cursor`. A saved view cannot be combined with other filters. Search and saved view evaluation are performed by Linear.
- `GET /v1/personal-tasks/{id}`: an issue by Linear identifier or `linear:`-prefixed identifier, including its full description.
- `GET /v1/personal-tasks/{id}/{section}`: independently paginated `comments`, `children`, `history`, `relations`, `inverse-relations`, and `attachments`. `GET /v1/personal-tasks/{id}/comments/{commentId}/replies` pages a comment's replies after checking that the parent belongs to the issue. History presently projects title, state, assignee, priority and description-change events; it does not claim every kind of Linear activity.
- `GET /v1/task-projects`, `/v1/task-cycles`, `/v1/task-views`, `/v1/task-inbox`: paginated personal collections. Reading the inbox does not mark it read.
- `GET /v1/task-metadata`: first page of choices with a `complete` flag per collection. If a flag is false, the client must not present that subset as complete.
- `GET /v1/task-options?kind=teams|users|states|labels|milestones`: paginated choices. Projects and cycles use the separate collection endpoints above.

Pages contain `items`, `nextCursor`, `observedAt`, and `paginationConsistency: "live"`. Cursors are tied to the filter and viewer. Linear can change between pages, so this is not a snapshot; clients should deduplicate by ID and refresh when needed. Individual issue label sets explicitly include `labelsComplete`.

The source uses fixed GraphQL documents and rejects partial/error responses instead of interpreting them as empty results. No live credential or task data was used for the fixture tests. The current notification relay does not accept Linear events; inbox data does not imply APNs delivery.

## Writes and reconciliation

`POST /v1/personal-tasks` creates an issue; `PATCH /v1/personal-tasks/{id}` updates allowed attributes. Both require `tasks:write`, an `Idempotency-Key`, and the `expectedViewerId` obtained when the draft was prepared. The Bridge refuses a different current viewer before reserving or writing, including on the first attempt. Create requires `teamId` and `title`; create/update accept `description`, `stateId`, `assigneeId`, `priority`, `estimate`, `dueDate`, `projectId`, `projectMilestoneId`, `cycleId`, `parentId`, `teamId`, and `labelIds`. Assignment does not start a worker. Unsupported fields are refused. Responses contain a minimal operation record; the client reads the issue for its current content.

`POST /v1/personal-tasks/{id}/comments` accepts `body` and optional `parentId`; the parent must belong to the same issue. `/relations` accepts `relatedIssueId` and `type` (`blocks`, `duplicate`, `related`, or `similar`), directed from the current issue to the related issue. `/attachments` accepts an HTTPS external `url`, `title`, and optional `subtitle`. Each requires the same viewer and idempotency fields as issue writes. Linear may upsert an attachment by URL: its confirmed `resultId` can differ from the reserved target; for an unknown result inspect the task's links. The app does not upload or proxy private Linear files yet and does not attach the personal token to external links.

Attribute updates follow Linear's last-write-wins behavior. An update containing `description` also requires the previously read `updatedAt` as `If-Match`. Immediately before the mutation, the Bridge reads the issue again. A mismatch returns 412 with the current issue so the client can compare it with its retained draft and obtain an explicit choice. This check is not an atomic Linear conditional update: a short race remains between the read and the write.

`GET /v1/task-operations/by-key` takes the original `Idempotency-Key` header; `/v1/task-operations/{operationId}` fetches a known operation, and `/v1/task-operations` lists unresolved operations for the same device and viewer. They require `tasks:write` and the expected personal viewer. If a Linear request may have arrived but no confirmed response was recorded, the operation stays `outcome_unknown` and is never sent again automatically. Create reserves a UUID before sending; the owner can use that target ID to investigate whether the issue exists. For an update, inspect the target and its activity before deciding.

After that investigation, `POST /v1/task-operations/{operationId}/resolve` with a new `Idempotency-Key` and `{ "confirmed": true, "resolution": "applied" | "not_applied" }` records the owner's conclusion. It does not make a Linear change. A live writer cannot be resolved as a crashed writer just because time elapsed. If the old process has stopped, an unfinished operation becomes unknown after the grace period; PID reuse may delay recovery. The original key remains unusable for another write after resolution.

The 0600 task ledger retains hashes, device/viewer/operation identifiers, target/result identifiers, times and states, never titles, descriptions, credentials or full responses. After seven days a completed request is no longer replayed, but a minimal tombstone prevents its key from silently executing again; unresolved records are retained until confirmed. The ledger has a 20,000-operation capacity and stops new writes when full; existing status checks and confirmations remain available. Loss or corruption of the ledger after initialization refuses new writes pending operator recovery. The local files are not tamper-proof against the same macOS user.
